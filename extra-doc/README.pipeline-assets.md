# Shared pipeline assets

CAPE stores shared, immutable pipeline assets in the meta-assets S3 bucket. The
bucket is created by CAPE infrastructure, but large asset payloads are not
managed as Pulumi `FileAsset` objects.

## Manifest layout

Keep one small JSON manifest per asset version under:

```text
assets/pipeline-assets/manifests/
```

The manifest records the upstream source, publication version, checksums,
expected sizes, consumers, and immutable publish prefix. The current Standard-8
manifest is:

```text
assets/pipeline-assets/manifests/kraken2-bracken-standard-8-2026-06-26.json
```

Its runtime S3 directory is:

```text
pipelines/shared/databases/kraken2-bracken/standard-8/2026-06-26/database/
```

Asset versions are immutable. A new upstream release adds a new manifest and a
new prefix; it never replaces an existing prefix.

## Planning a publication

The portable Python publisher currently supports archived database assets. It
validates all manifests and produces a deterministic aggregate plan without a
transfer by default. It has no Pulumi dependency:

```bash
python -m pipeline_assets.publisher \
    --manifest-dir assets/pipeline-assets/manifests \
    --bucket <meta-assets-bucket>
```

Limit the plan to one asset with `--asset-id`:

```bash
python -m pipeline_assets.publisher \
    --asset-id kraken2-bracken-standard-8 \
    --bucket <meta-assets-bucket>
```

Use `--publish` with one asset ID to download into temporary scratch, validate
the upstream checksum and database contents, upload the immutable `database/`
directory, and write its generated manifest last:

```bash
python -m pipeline_assets.publisher \
    --asset-id kraken2-bracken-standard-8 \
    --bucket <meta-assets-bucket> \
    --publish
```

The archive and expanded database must not be kept in the repository. For
long-running publication, invoke the same package from an AWS-hosted job with
role-based credentials rather than a short-lived developer session.

## Specific tools

Tool-specific asset instructions belong in subsections under this heading. Add
another subsection when a pipeline needs integration beyond the shared manifest
and publisher workflow.

The current implementation has one archived-database publication path and one
consumer-specific runtime projection for taxprofiler. It does not yet provide a
generic publication-adapter or consumer-integration framework. The boundary
iteration is tracked in [issue #386](https://github.com/cape-ph/cape-cod/issues/386).

### Taxprofiler database sheets

Generate a small taxprofiler database sheet from the deployed runtime export:

```bash
python -m pipeline_assets.database_sheet \
    --manifest assets/pipeline-assets/manifests/kraken2-bracken-standard-8-2026-06-26.json \
    --runtime-export cape-pipeline-runtime-export.json \
    --output databases-standard-8.csv
```

The generated sheet contains the resolved meta-assets bucket and immutable
asset prefix. It should be generated by the environment deployment flow or
kept as a temporary run input, not embedded with a physical bucket name in a
pipeline fixture.

## Pulumi and deployment ownership

Pulumi owns the shared bucket, IAM, lifecycle rules, and the stack output that
identifies the bucket. Pulumi should not perform the large download. A manual
command, CI job, or the future `cape-cod-env` deployment can invoke the
portable publisher after the infrastructure exists.

### Transitional ownership until `cape-cod-env`

Until [issue #387](https://github.com/cape-ph/cape-cod/issues/387) is complete,
pipeline asset publication remains an out-of-band environment-owner step. The
current Standard-8 asset is already published at the immutable prefix above, so
this deployment needs no post-Pulumi publication. New asset versions require
the standalone publisher and immutable-prefix verification before use. Do not
republish an existing prefix. Remove this subsection when the Ansible handoff
is operational.

The publisher target should come from the Pulumi environment handoff rather
than a physical bucket name in a pipeline fixture. The asset manifest remains
portable when publication moves from `cape-cod` to `cape-cod-env`.

The eventual migration moves the manifests, publisher package, and database
sheet generator into `cape-cod-env`. Published S3 objects and the runtime export
schema remain unchanged.

## Reproducibility

Runtime references should use an explicit asset ID and version. Do not use a
mutable `latest` path for an analysis run. Record the selected manifest and
content digest with the run metadata. Retain old asset versions while analyses
or reports reference them.
